# DEALT / SLIDE — Gameplay-Aligned Development Plan

**Author:** Manus AI  
**Prepared:** 2026-08-20  
**Baseline:** Draft PR #114 (`cursor/game-experience-enhancement-cb34`) over protected default branch `main-tL2525`

## Product Thesis

**DEALT / SLIDE is a phone-operating-system strategy game whose mini-games must all alter one shared empire state.** The core loop is: scout or claim a block, place a crew, earn and protect cash, manage the weekly books, and confront a named rival. DRIVE is the high-intensity execution layer; MAP, SHOEBOX, CREW, and the economy systems make its outcomes meaningful.

> The game should not pursue a general-purpose military-shooter scope. Its credible shooter standard is a polished, replayable **drive-by action vertical slice** with responsive shooting, readable targets and cover, fair consequences, a distinct target/location, meaningful enemy behavior, and persistent results in the empire.

## Definition of a Credible DRIVE Shooter

The present game is an action prototype rather than a finished shooter. The following gate defines the first credible shooter vertical slice for this product.

| Capability | Required playable behavior | Evidence of completion |
|---|---|---|
| Input and weapons | Aim/fire is responsive; at least two weapon behaviors differ in cadence, reload, spread, damage, and ammunition use. | Input and weapon-state tests; a short playthrough without stuck input or frame-dependent firing. |
| Enemy encounters | Named rivals have health, cover/useful movement, return-fire telegraphs, and a small encounter objective beyond clearing random targets. | Deterministic encounter test and a visible encounter setup screen. |
| World and readability | Every hero block uses an authored location plate, depth/cover geometry, actor silhouettes, hit feedback, and a clear car/window view. | Screenshot/video comparison against the art/camera contract. |
| Consequences | Success, failure, civilians, property damage, ammunition use, heat, injury, and loot update the shared empire state and Shoebox ledger exactly once. | Integration tests covering completed and failed encounters. |
| Progression | Crew role, equipment, health, and block defense visibly affect encounter loadout or outcome. | Two controlled scenarios demonstrating different results. |
| Reliability | Pause/restart/exit are safe; no duplicate loops, duplicate rewards, stale targets, or persistence loss occur. | Regression tests, browser smoke test, and production build. |

## Delivery Sequence

### Milestone 0 — Reconcile and Review the Current Empire Pass

The immediate task is to finish the explicit Shoebox requirement inside draft PR #114: show every crew member, their weekly cost, their attributable weekly earnings, their net contribution, deployment status, and current strip. All player-facing money movement should use a single vault-routing boundary, so the Shoebox activity and spending categories accurately reflect payroll, market/stash purchases, bail/hospital, bribes, seizures, collections, and transfers.

Acceptance requires that an active deployed dealer, an enforcer, and an off-block shooter all appear in the same Shoebox list with correct, explainable values. The existing aggregate role cards and block rows remain summaries; the new member rows are the audit detail behind them. This work should be added to the current draft rather than recreated separately.

### Milestone 1 — A Living Opponent

Implement issue #81 as a narrow but complete rival crew slice. Create one named persistent crew with a behavior card, treasury, roster, claimed DNA-backed block, grudge score, and event history. On the world tick, it must choose among claim, reinforce, lay low, or retaliate using the same income, wage, heat, and territory constraints as the player. A three-tick idle scenario must visibly change the map and city feed, while a player win must reverse that change through the normal combat result path.

### Milestone 2 — Location Variety Before Map Scale

Complete issue #80 as a five-to-ten-card initial Block DNA library, then grow to thirty to forty cards. Each card must declare geometry, income multiplier, heat risk, cover, lighting, event modifiers, destruction mask, and an authored presentation plate. The map chooses cards by tier/area; DRIVE and block placement consume the same DNA. Mapbox remains an optional discovery and presentation surface.

### Milestone 3 — DRIVE Vertical-Slice Upgrade

Build the credible shooter gate above on one DNA card first. The order is weapon-state and deterministic encounter model; enemy/cover/telegraph behavior; authored renderer and actor presentation; then economy/heat/injury/result persistence. Do not add a second combat mode until the first has browser-verified consequences in MAP and SHOEBOX.

### Milestone 4 — Visual and Technical Release Gate

Resolve issues #77–#79: the art bible and camera contract, manifest-only runtime assets, placeholder/emoji retirement, alpha/chroma cleanup, asset budget, performance profiling, error states, and tester release checklist. Treat #45 as the release umbrella rather than a feature bucket.

## Mini-Game Ownership and Integration Contract

Individual games should be developed as independent React modules, but they must never own a disconnected economy or territory copy. The navigation ID selects the module in `App.tsx`; the module reads/writes an explicit shared-store contract and emits a typed outcome for the calling system.

| App ID | Surface | Owns | Must read from | Must write to |
|---|---|---|---|---|
| `map` | Territory control | Recon interaction and placement intent | blocks, crew, Shoebox summary, rival state | block placement, selected target, claim/collect outcomes |
| `shoebox` | Cash App-style vault | Transfer UI, financial reporting, ledger view | player street cash, crew, blocks, ledger | only the money-router boundary |
| `driveby` | Shooter encounter | Per-encounter input, weapon state, encounter presentation | selected target, crew loadout, Block DNA | one atomic encounter result |
| `slide` | Grid combat | Turn/placement combat interaction | shared block and crew state | one atomic combat result |
| `dealt_v2` | Dealing loop | Customer/deal decision | stock, member skill, heat | cash/inventory/heat event |
| `alchemy` | Crafting | Recipe and inventory transformation | inventory | inventory and heat event |
| `gang_hq` / `contacts` | Crew management | Recruitment, equipment, availability | money router, roster | crew roster/loadout/status |
| `market`, `trap`, `casino`, `missions` | Supporting loops | Their own UI decisions | inventory, crew, money | typed ledger plus inventory/crew/event result |
| `raid`, `graffiti`, `bipndip`, `cocaine_crush` | Optional mini-games | Session-only mechanics | prerequisite state | typed outcome; no direct ad hoc cash mutation |

The practical workflow is to work within the module folder and its nearest pure utility/tests, then update only the contract boundary it consumes. New mini-game work starts with a one-page brief: player decision, input, duration, success/failure states, exact shared-state inputs, exact typed outputs, tests, and a browser proof. The app icon is added only after that module can produce an economy, territory, crew, inventory, heat, or rival outcome; otherwise it belongs in a hidden/debug route rather than the home screen.

## Review and Merge Policy

No direct commits go to `main-tL2525`. The current PR remains draft until the active slice is committed, pushed, checked, visually smoke-tested, and reviewed. When its evidence is complete, change the PR from draft to ready for review; merge only after an owner/reviewer decision and all required checks remain green. The stale `copilot/connect-player-locations` branch is already equivalent to default and can be deleted as housekeeping; the preserved rollback branch documented in the project log must remain.

## Risks and Controls

| Risk | Control |
|---|---|
| Two cash stores drift apart | All new money movement goes through `moneyRouter`; direct cash mutations are catalogued and migrated incrementally. |
| Scene presentation outpaces gameplay | Use Block DNA and encounter-model acceptance tests before adding visual-only effects. |
| Mini-games become disconnected icons | Require typed shared-state input/output contracts before home-screen availability. |
| Map token/API availability blocks play | Preserve the offline tactical map and authored DNA cards as the complete gameplay path. |
| A large branch is merged without review | Keep PR #114 draft until automated, browser, and reviewer evidence is attached. |
| Runtime stability regresses | Validate persistent state, restart/exit, test suite, production build, and browser smoke path for every combat/economy increment. |
